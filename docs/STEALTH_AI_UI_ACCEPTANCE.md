## 實際完成流程

1. 兩位使用者各自在畫面建立分身，明確啟用偷揪、關閉測試帳號的安靜時段，
   不啟用示範配對。第三人保留為未參與者。
2. 需求者輸入熱湯正餐需求，本機 `qwen3.5:4b` 補問地點、相對時間、長度與預算。
   補充後逐項檢查表單，確認東側門、60 分鐘後、120 分鐘、預算 150、費用未知，
   願意下單／分食、不取餐；修訂摘要與標籤後親自儲存。
3. 資源者透過同一模型整理正餐／優惠券資源：同地點與相容時間、每人報價 90、
   預算 150，願意提供優惠券、分食、下單與取餐。核對套用表單後儲存。
4. App 顯示一組私人兩人配對，規則分數 80，已知費用 90，優惠券條件仍待確認。
   原始需求僅顯示本人內容。
5. 點「AI 語義排序與判讀」：實際執行 `qwen3-embedding:0.6b` 與本機候選模型，
   顯示相似度 0.595、地點／時間／分類／取餐志願理由，以及優惠券待確認事項。
   因優惠券仍未驗證，判讀維持「資訊不足，仍需確認」，沒有宣稱優惠已生效。
6. 分身自動草案使用每人 90／全團 180，沒有拿 150 元預算當售價；建議成員 1 下單、
   成員 2 取餐。此草案是免費規則規劃器，不是大型模型報價或任何人的承諾。
7. 雙方分別點「我有意願」。需求者修改公開說明、提出第一版方案；提出後同意數為 0/2。
8. 需求者勾選確認並同意第一版。同意數為 1/2，沒有建團；SQL 也確認 formed_post_id 為 null。
9. 資源者修改方案：每人費用改為 95、填寫至少五字調整原因、下單者改為成員 2，
   取餐仍由成員 2 負責。未填原因前送出按鈕停用。
10. 提出第二版後舊同意全部清除，畫面與 SQL 都是 0/2，仍沒有拼單。
    資源者先同意第二版，需求者登入後仍必須重新勾選與同意第二版。
11. 雙方同意同一版本後自動建立一筆正式拼單：每人 95、2/2 人、更新後的下單與取餐者，
    公開內容沒有私人需求原文或本組費用調整原因。
12. 需求者從「查看正式拼單」開啟聊天室並傳訊；資源者從「訊息」收件匣讀到同一訊息並回覆。
13. 第三人偷揪頁看不到該私人配對；直接開啟成團聊天室網址也被拒絕，沒有訊息或輸入框。

核心操作均由 App 畫面完成；補充用一般使用者 API session 核對雙方訊息、最終版本／費用／分工，
以及重送兩次第二版同意仍回傳相同拼單。SQL 確認僅一筆隔離成團貼文。

## 發現並修正

- **未知費用重複補問**：模型可能遺漏正確摘錄，對明說的「費用未知」又要求報價。
  現在核對本人明確的未知宣告；後續若有新報價／總價，仍走既有金額驗證，不會抹掉較新的報價。
  未知保持 null，不推算成免費，也不轉用預算。
- **摘要地點與欄位矛盾**：模型偶爾抄到範例的「正門」，但地點欄位是東側門。
  現在查核本人地點陳述與否定語句；無依據的地點清空補問，摘要內不符地點也會修正並提示。
- **候選理由超出已知事實**：最初向量成功，但模型誤稱價格／下單／取餐資訊缺失，被原檢查擋下。
  現在每次將 JSON schema 的理由列舉縮限到該候選已核對的 facts，要求至少一項；
  原本輸出驗證、未知事項強制待確認、推論後版本／權限檢查全部保留。
  修正後在 App 重跑，候選判讀完成且顯示真實理由與優惠券待確認事項。

本機 4B 模型仍可能遺漏前文而再次補問；需求者本次經五輪整理才可套用，資源者一次完成。
模型產出的摘要與欄位仍須本人核對，沒有自動儲存或替人承諾。
