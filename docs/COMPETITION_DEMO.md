# 偷揪競賽展示與本機效能演練

這份文件描述可重跑的合成情境，與正式 App／Supabase 驗收分開。
不部署、不使用付費模型；Apple 裝置模型尚未整合。

## 六分鐘展示順序

1. **30 秒問題**：想吃一點熱食的人、有可分享餐點的人、會順路取餐的人，通常不會各自發文找彼此。
2. **90 秒分身訪談**：A 說想吃熱湯、120 元預算、願意下單；B 有熱湯每人 80 元；C 願意順路取餐。
   每人明確提供 60 分鐘後開始、可配合 120 分鐘、正門。C 若被問分類，補「餐點分類是正餐」。
   展示已提供的時間、預算與角色仍保留；不把路過當成願意取餐。
3. **60 秒機會**：從已授權需求找到互補組合，展示語義排序／理由及待確認事項。
   App/Supabase 現在是規則先找合法候選，再由向量與模型排序判讀；不是全庫向量發現。
4. **90 秒確認**：費用 80 元、三人共 240 元，A 下單、C 取餐，逐人確認同一版。
   只兩人同意不能建團；改費用或分工，舊同意歸零。最後一人確認才建立正式拼單及聊天室。
5. **60 秒邊界**：展示同版衝突保留草稿、撤回失效、過期拒絕或斷線重試之一。
   沒有替任何人實際訂餐、付款或承諾取餐。
6. **30 秒成果**：說明 AI 降低需求整理負擔、讓供需與行程能被一起比較；交易規則仍由程式保護。

真實 App 展示請使用專用隔離帳號，勿展示真人私人需求或管理回報。
先確認展示時間、模型狀態、分身安靜時段與邀請配額；不能用已過期的舊配對假裝即時成果。

## 一鍵重跑／重設的本機合成演練

Windows：`.venv\Scripts\python.exe scripts\competition_demo.py`

Mac：`.venv/bin/python scripts/competition_demo.py`

每次建立全新的暫存 SQLite，演練三個已確認的合成角色，驗證未同意不能形成、
三人同意後形成及重送回相同 ID；結束自動清理資料庫，不碰 Supabase 或既有示範資料。
預設不呼叫模型，不得把這個結果說成模型效果或正式 App UI 驗收。

加 `--run-local` 才使用已安裝的免費 `qwen3.5:4b` 訪談三個合成角色，沒有模型下載。
原始與補答後結果都記錄在 `.local/competition-demo-latest.json`，不隱藏初次缺項。
模型輸出僅作證據，演練成團使用事先確認的合成人物條件，不把模型結果自動當真人同意。
2026-10-20 真實本機結果：A、B 一輪無缺項；C 首輪缺餐點分類，補答後三人皆可核對草稿。
這三例不是一般使用者準確率。CLI 使用的是隔離 local prototype adapter；
目前 App/Supabase 的改版同意流程以 `STEALTH_AI_UI_ACCEPTANCE.md` 為驗收依據。

## AI 與程式各自負責

```mermaid
flowchart LR
  U[本人自然語言] --> API[登入與權限檢查]
  API --> Q[有上限的本機模型佇列]
  Q --> I[理解與補問草稿]
  I --> C[本人核對並儲存]
  C --> DB[Supabase 私人需求]
  DB --> R[必要條件篩選]
  R --> S[免費向量排序與候選判讀]
  S --> T[費用與分工方案]
  T --> A[全員確認同一版]
  A --> G[交易建立拼單及聊天室]
```

Apple 可留待 Mac 實作個人理解；跨使用者權限與多人配對仍由後端處理。
不能宣稱已做跨分身自主談判、全庫雲端向量搜尋、付款或 Apple 原生推論。

## 評估與效能怎麼說

- 理解：`scripts/evaluate_local_intake.py` 的 standard／challenge 合成集，列出欄位缺漏、錯誤與延遲。
- 檢索與判讀：`scripts/evaluate_semantic.py` 固定 12 題檢索、6 題判讀，預設 dry run，
  明確加 `--run-local` 才跑本機模型。以實際報告日期與案例數說明，不能當真實使用者滿意度。
- 多人安全：三人同意、改版重認、版本衝突、撤回、方案與邀請過期、斷線重試有獨立驗收紀錄。
- 不宣稱已節省多少錢或提升多少成團率；要用真人授權實驗比較填寫時間、完成率、修改次數才能回答。

`python scripts/benchmark_local.py --posts 500 --attempts 8` 不呼叫模型或網路，
以暫存 SQLite 產生 500 貼文、讀取 30 次首頁、8 人同時競爭最後一席。
輸出 `.local/benchmark-latest.json`；資料庫自動移除，上限為 2000 貼文與 16 個請求。
2026-10-20 此 Windows 一次結果：建立 2.599 秒、首頁 p50 0.689 ms／p95 1.008 ms、
最後一席 1 成功／7 拒絕，沒有超收。這是直接呼叫 SQLite adapter，沒有 HTTP 延遲，
不是 Supabase、PostgreSQL、雲端主機或手機承載能力，也不是跨機器比較基準。

模型現在單程序同時一筆、FIFO 最多等待兩筆、等待上限五秒；滿載／逾時仍回可重試 busy。
只存入記憶體票號與計數，不持久化提示詞；不是背景任務服務、跨程序佇列或無限等待。
此版維持單程序／單實例；真正雲端併發與長時間壓測仍待獨立規劃。
已用離線測試演練雲端環境／TLS 代理設定；沒有建置 Linux Docker 或部署主機。
