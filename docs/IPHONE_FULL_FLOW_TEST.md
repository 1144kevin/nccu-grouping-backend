# iPhone 完整驗收：鍵盤 → 拼單 → 聊天 → 偷揪 AI → 成團

2026-10-22。本人已確認：用電腦 Google 登入設定 App 密碼後，同帳號可以登入 Expo Go。以下操作使用 Supabase 開發專案；App、API、模型維持本機，不部署、不付費。

## 0. 先驗鍵盤，再做功能流程

Expo Go 重新載入目前專案即可，不要登出、清除儲存或重裝 App。新 JavaScript 已可由目前的 Metro 產生。

| 畫面 | 操作 | 通過條件 |
| --- | --- | --- |
| 新增貼文 | 文章輸入多行，繼續點底部欄位、地點搜尋，再打開新增標籤 | 正在輸入的文字在鍵盤上方；表單可捲動；標籤視窗的輸入與按鈕可達 |
| 偷揪 → 我的需求 | 點「跟分身說需求或補充資訊」、下方數字欄位及費用分工欄位 | 多行文字與數字不被遮住，能捲到確認按鈕 |
| 聊天室 | 輸入長句、換行、傳送；上下查看訊息，再收起鍵盤 | 輸入列及傳送按鈕在鍵盤上方，關閉後沒有大片空白，文字不會消失 |
| 登入／個人資料 | 下方輸入框、App 大字級（若使用） | 能看見游標與輸入文字，不影響原帳號與內容 |

捲動表單可互動收起 iOS 鍵盤；聊天室拖動訊息列表也可收起。表單使用 iOS 原生自動鍵盤 inset，聊天室使用量測視窗座標的避讓，沒有重複加兩份鍵盤高度，也沒有新增原生依賴。

目前程式檢查：48組／206項前端測試、TypeScript、變更檔 ESLint 通過；iOS JS 套件回200且包含修正。2026-10-22 本人重新載入 Expo Go 後回報「已正常，輸入框不再被遮住」，鍵盤遮擋問題已有實機確認；尚不代表表中每個畫面與完整功能流程都已逐項驗收。若其他欄位有問題，回報「頁面、欄位、鍵盤打開或換欄位時發生、能否手動捲上去」，不要附帳密。

## 1. 準備兩個自己能操作的帳號

- **A：iPhone Expo Go**，使用目前已登入的帳號。
- **B：電腦 Web**，用另一個測試帳號。電腦開 `http://localhost:8082/sign-in`，Google 登入時選另一個信箱；若已登入 A，先在電腦登出。完成後開 `http://localhost:8082/` 操作 App。
- 不要讓 A、B 使用相同帳號；否則無法測申請接受、跨帳號聊天與全員同意。沒有第二個信箱時，先完成單帳號發文、訪談與示範觀察；不能把它記成多人驗收通過。
- 也可用同一支手機輪流登出 A／登入 B，但第二個帳號須先設定 App 密碼。兩個裝置同時操作較容易核對。
- 電腦和手機維持目前私人熱點。API／Expo Go／模型視窗保留；手機在前景時才依既有機制更新，尚無背景推播。

確認畫面有「Supabase 開發版」及本人名稱。測試文章加上唯一標記，例如 `[實機測試_1022_01]`；內容註明不是真實訂購。先不附圖，確定文字流程後再加測自己的非敏感測試圖片。

目前已檢查本機模型服務回200，已安裝 `qwen3.5:4b` 與 `qwen3-embedding:0.6b`，裝置 AI 與語義配對皆啟用。Expo Go 使用 Windows 模型，Apple 裝置端 AI 留在原生 App。

## 2. 一般拼單：新增 → 申請 → 接受

1. **A** 點底部「新增貼文」，填入：
   - 內容：`[實機測試_1022_01] 測試一起訂晚餐，政大正門取餐，每人90元，僅供內測，不會實際訂購。`
   - 標籤：晚餐；需求人數：**2人，包含主揪**。
   - 截止：至少一小時後；地點：在地點搜尋選定「政大正門」的實際結果，不能只打文字而不選結果。
   - 「每人預估金額」填90；不要加入真實付款資料。
2. 點「發布」。回首頁或「我的拼單 → 我主揪的」確認文章存在，重整後仍在。
3. **B** 用唯一標記搜尋文章，打開詳情，點「想被揪」。應顯示待主揪接受、尚未占名額；B 此時不應有團員聊天室存取。
4. **A** 到「我的拼單 → 我主揪的」，開文章，找到 B 的申請，點「接受」。若舊畫面尚未更新，重新整理一次。
5. **A、B** 重新整理，應顯示2人／已額滿；B 在「申請／已加入」看得到。滿團文章不應出現在可加入的推薦結果中，但主揪管理仍能查看。

額外測試可分開另開文章：拒絕一筆申請、取消待審申請、發文後在尚無申請時編輯條件。不要把這些分支與主要成功案例混成同一筆，方便查核。

## 3. 聊天：跨帳號送收 → 恢復 → 退出

1. **A、B** 從同一筆拼單詳情按「進入拼單聊天室」。
2. **A** 傳 `A：測試18點在正門見。`，**B** 傳 `B：收到，這是測試。`。兩邊重新整理後應看見彼此訊息，姓名正確，沒有重複訊息。
3. **A** 測一段多行訊息：鍵盤不能蓋住輸入列或傳送按鈕。離開聊天再進入，已送出的內容仍在。
4. **A** 在聊天室打一段未送出的測試文字，短暫關閉手機行動數據（目前此手機是熱點，Windows 連線也可能受影響），嘗試傳送後恢復連線。只有確實遇到連線失敗時，才驗「草稿保留、恢復後重試、不重複送出」。不要把單純關閉行動數據視為保證切斷私人區網；也不要改防火牆或憑證。
5. **B** 在截止前回拼單詳情按「退出並釋出名額」。A 重整後應恢復一個空位；B 重新讀取聊天室應被拒絕，而非繼續存取私人訊息。
6. **A** 只對這篇測試文章使用「取消這筆拼單 → 確認取消拼單」。主揪的既有聊天室應變唯讀；不會刪掉歷史。

若只想先完成成功流程，可把第4–6步留到最後，以免在下一步還需要這個聊天室時已退出。

## 4. 偷揪：建立分身與兩筆相容需求

**兩個帳號** 都打開選單「偷揪 · 我的 AI 分身 → 我的分身」：

1. 設名稱與外觀；探索範圍選「多探索一些」。
2. 啟用偷揪；本輪先關閉安靜時段，避免剛好被靜音；每日上限保留足夠次數。
3. 不勾「也接受清楚標示的示範配對」，避免把假人物當 B。按「儲存我的分身」。

接著各自到「我的需求」。可把下面文字分別貼到「跟分身說需求或補充資訊」，按「讓本機分身理解」。

**A：需求者**

> 這是內測。我需要找人一起吃晚餐，正餐類，在政大正門取餐。從60分鐘後開始，可配合120分鐘，每人預算上限120元，實際價格還不知道。我願意一起分食，不負責下單或取餐。共同標籤是晚餐，沒有必要飲食限制。

**B：資源與分工提供者**

> 這是內測，沒有實際訂單。我有可分食的正餐資源，每人已知費用90元，在政大正門取餐。從60分鐘後開始，可配合120分鐘，每人預算上限120元。我願意下單，也願意順路取餐和一起分食。共同標籤是晚餐，沒有必要飲食限制。

若模型補問，只補它列出的缺項；例如價格未知就明確說「價格未知」，不能把預算120當成售價。已確認資訊應保留。可故意補一句「預算改成130元，其餘不變」，檢查只更正預算，測完再改回120。

資訊足夠後按「套用到下方表單，逐項檢查」，核對：

| 欄位 | A | B |
| --- | --- | --- |
| 類型 | 我需要 | 我擁有 |
| 分類／地點 | 正餐／政大正門 | 正餐／政大正門 |
| 延遲／可配合 | 60分鐘／120分鐘 | 60分鐘／120分鐘 |
| 預算上限 | 120 | 120 |
| 已知費用 | 留白未知 | 90 |
| 願意角色 | 一起分食 | 下單、取餐、一起分食 |
| 標籤 | 晚餐 | 晚餐 |

AI 不保證每次都完全抽對；不正確時手動修正，再按「確認需求並交給分身」。這一步才把本人核對後的需求存入開發資料庫，單純訪談或套用沒有自動儲存。

## 5. 偷揪：語義搜尋 → 理由 → 修改方案 → 全員同意

1. **A、B** 到「偷揪結果」，各按一次「AI 搜尋新配對機會」，建立自己的需求向量。對方也做完後若仍沒結果，等30秒再重試；必要時按「讓分身找機會」或右上重新整理。不要連續狂按模型請求。
2. 出現包含你們兩人的有效機會後，按「AI 語義排序與判讀」。應看見互補理由與待確認事項。規則排序分數不等於成團成功率，也不能把模型猜測當作已確認事實。
3. **A、B** 各按「我有意願」。這只代表有興趣，尚未建立正式團。
4. 查看「分身自動提案 · 費用與分工草案」。目前基本費用／分工草案由免費規則規劃器依已確認資料提出；本機文字模型負責訪談及候選判讀，不要把草案全都算成模型生成。
5. **A** 核對公開說明，設定每人90元，指定 B 的成員代號為下單與取餐者，選有效截止時間，按「提出方案，請全員確認」。先看畫面「你是成員幾」，不要假定 B 永遠是成員2。
6. **A** 勾選確認費用、分工及公開內容，按「同意第1版並等待成團」。**B先不要同意**。應顯示1／2，不能先產生正式拼單。
7. **B** 按「修改方案（清除所有舊同意）」，把費用改成95元，原因填「內測調整取餐費用」，保留分工，提出新版。兩邊重整後應顯示新版、同意歸零，A舊版同意不能沿用。
8. **A、B** 各核對新版，重新勾選並同意。第二個人的同意成功後，應出現「全員已同意，拼單與聊天室已建立」。
9. 各按「查看正式拼單」、「進入成團聊天室」，核對人數2人、95元、主揪與分工，傳一則測試訊息。重整偷揪頁不應多建立第二筆相同拼單。

方案與邀請有期限，建議成團部分30分鐘內完成。若失效，不要改手機時間或繞過限制；另建新的相容需求。示範人物不能同意，所以示範配對無法完成這個成團案例。

## 6. 進階情境、清理與回報

- **三人成團**：再準備 C 帳號，三方先各自建立相容需求，再搜尋；既有雙人邀請不會因為 C 後來加入就自動變三人，請核對卡片人數，必要時重開需求。三人都必須同意同一版。
- **同時修改**：A、B先各自載入相同版本；A先提交，再由B提交舊版本。B應看到版本更新提醒並保留草稿，不能蓋掉A的新方案。
- **撤回／過期**：用另一筆測試需求驗「撤回我的意願」或「撤回需求並使配對失效」；重整後不能再同意舊邀請。不要在唯一的成功案例做到一半時撤回。
- **模型暫時失敗**：訪談文字、手動需求與既有配對仍可保留重試。能手填不代表 AI 驗收通過；模型服務仍須在 Windows 執行。
- 測完只撤回本輪未消耗需求、取消本輪測試拼單。不要用全站清理、刪帳號或刪除既有示範資料來收尾。
- 回報問題時提供「A或B、頁面、點了哪顆按鈕、錯誤文字、文章測試標記、約略時間」。不要傳密碼、Token或驗證信完整網址。

這輪主流程的通過標準：兩人真正登入不同帳號、申請接受後互相聊天、本人確認需求、AI有排序理由與待確認事項、改版要求重新同意、全員同意後只建立一組正式拼單與聊天室。沒有真的訂購、扣款、部署或 Apple AI 驗收。
